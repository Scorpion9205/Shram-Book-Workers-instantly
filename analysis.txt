1. EXECUTIVE FORENSIC SUMMARY
--------------------------------------------------------------------------------
Following a comprehensive audit of every component, route, service, repository, 
hook, and page across both the frontend (Next.js 15) and backend (Express 5 + Prisma), 
the system demonstrates strong domain modeling, cryptographically secure OTP generation, 
atomic wallet balance transactions, and strict TypeScript compilation (0 errors across 
both repos with 38 passing Vitest unit tests).

HOWEVER, several core end-user features are silently broken or completely disconnected 
between the UI and API layers. Most notably:
1. All search bars (Address Search, Job Feed Search, Admin User Search by Role, and 
   Admin Booking ID Search) fail to execute their intended function due to missing 
   hook implementations, ignored query parameters on the backend, or casing mismatches.
2. The Work-Start OTP input in the Worker UI is hard-limited to 4 digits (`maxLength={4}`), 
   while the backend produces 6-digit secure OTPs, locking workers out of starting jobs.
3. Online Razorpay payments lack a client-side verification endpoint (`/payments/verify`), 
   relying solely on external webhooks which fail in local development or unstable networks.
4. Worker live location socket broadcasts (`worker:location_update`) are ignored by the 
   backend Socket.IO server, and the Provider live tracking card is an unrendered placeholder.
5. Worker Wallet management has a fully operational backend API, but zero frontend UI pages.
6. The Agent bookings query in `BookingController` fails because `agentId` is queried against 
   `User.id` instead of `AgentProfile.id`.

2.1 Address & Location Autocomplete Search Bar (CRITICAL FAILURE)
--------------------------------------------------------------------------------
Affected Components:
- `frontend/src/components/ui/AddressSearch.tsx`
- `frontend/src/hooks/useGoogleMapsScript.ts`
- `frontend/src/app/(provider)/provider/instant-hire/page.tsx`
- `frontend/src/app/(provider)/provider/jobs/create/page.tsx`

Root Cause:
1. In `frontend/src/hooks/useGoogleMapsScript.ts` (lines 11-13):
   ```typescript
   export function useGoogleMapsScript() {
     return false; // Hardcoded stub!
   }
   ```
   The hook literally returns `false` constantly. It never injects the Google Maps Places 
   script (`https://maps.googleapis.com/maps/api/js?key=...&libraries=places`).
2. In `AddressSearch.tsx` (lines 34-39):
   ```typescript
   const isMapsLoaded = useGoogleMapsScript();
   useEffect(() => {
     if (!isMapsLoaded || !inputRef.current || !window.google?.maps?.places) return;
     const autocomplete = new window.google.maps.places.Autocomplete(inputRef.current, ...);
   ```
   Because `isMapsLoaded` is always `false`, the Google Places Autocomplete instance 
   is NEVER created. No suggestions dropdown ever renders when the user types.
3. Fallback Lat/Lng Corruption (lines 128-133 of `AddressSearch.tsx`):
   When the user types an address manually, the component executes:
   ```typescript
   onChange({
     address: val,
     lat: 0,
     lng: 0,
     placeId: "manual_input",
   });
   ```
   It passes `lat: 0, lng: 0` (Null Island in the Atlantic Ocean) to the form state!
4. Downstream Impact:
   - In `instant-hire/page.tsx`, the request is sent with `latitude: 0, longitude: 0`.
   - In `jobs/create/page.tsx`, the job is posted with `latitude: 0, longitude: 0`.
   - The backend spatial index (`Redis Geo` / `InstantMatchingService`) searches for 
     workers within radius of (0, 0). It never finds any workers, causing the instant hire 
     flow to hang forever in the "Searching nearby workers…" loading state!

Remediation Required:
- Implement dynamic script loading in `useGoogleMapsScript.ts` with error handling.
- Provide a robust OpenStreetMap (Nominatim) or browser-geocoded fallback in `AddressSearch.tsx` 
  when Google Maps API key is absent or invalid, resolving real lat/lng coordinates.

2.2 Worker Job Feed Search Bar & Filters (CRITICAL FAILURE)
--------------------------------------------------------------------------------
Affected Components:
- `frontend/src/app/(worker)/worker/jobs/page.tsx`
- `frontend/src/components/forms/JobFilterBar.tsx`
- `frontend/src/features/jobs/jobsApi.ts`
- `backend/src/modules/jobs/routes/job.routes.ts`
- `backend/src/modules/jobs/controllers/JobController.ts`
- `backend/src/modules/jobs/services/JobService.ts`

Root Cause:
1. Frontend Query Generation:
   In `jobsApi.ts`, `getJobs` builds a query string with filters:
   `GET /api/v1/jobs?search=carpenter&category=carpentry&sort=latest&page=1&pageSize=12`
2. Backend Controller Disconnect (`JobController.ts`, lines 23-27):
   ```typescript
   getAllJobs = async (req: Request, res: Response): Promise<void> => {
     const user = (req as any).user;
     const result = await this.jobService.getAllJobs(user.userId);
     this.ok(res, result.jobs, 'Jobs retrieved successfully');
   };
   ```
   `JobController.getAllJobs` completely DISCARDS `req.query`!
   It does not read or validate `search`, `category`, `minSalary`, `sort`, or pagination.
3. Backend Service Disconnect (`JobService.ts`, lines 61-119):
   `getAllJobs(userId: string)` takes only `userId`. It extracts worker skills and executes:
   ```typescript
   const jobs = await this.jobRepo.findManyOpenBySkillIds(skillIds);
   const result = { jobs };
   await this.cache.set(cacheKey, result, 120);
   return result;
   ```
   It queries all open jobs matching skill IDs with ZERO search term matching, and caches 
   the entire array in Redis for 120 seconds.
4. Input UX Bug in `JobFilterBar.tsx` (lines 20-25):
   `<Input defaultValue={filters.search} ... />` is an uncontrolled input that desynchronizes 
   from the parent filter state.

Remediation Required:
- Create `GetJobsQueryDto` validating `search`, `category`, `minSalary`, `maxSalary`, `sort`, `page`, `limit`.
- Pass the filter DTO from `JobController` to `JobService.getAllJobs(userId, filter)`.
- Update `JobRepository` to execute Prisma filters with `contains` (case-insensitive) on title/description.
- Update `JobFilterBar.tsx` to use controlled inputs (`value={filters.search || ""}`).

2.3 Admin User Directory Search & Role Filter (VALIDATION 400 FAILURE)
--------------------------------------------------------------------------------
Affected Components:
- `frontend/src/app/(admin)/admin/users/page.tsx`
- `backend/src/modules/admin/controllers/AdminController.ts`
- `backend/src/core/enums/Role.ts`

Root Cause:
1. In `AdminUsersPage` (`admin/users/page.tsx`, lines 84-88):
   ```tsx
   <select value={roleFilter} onChange={(e) => setRoleFilter(e.target.value)}>
     <option value="">All Roles</option>
     <option value="worker">Worker</option>
     <option value="provider">Provider</option>
     <option value="agent">Agent</option>
   </select>
   ```
   The option values are LOWERCASE (`"worker"`, `"provider"`, `"agent"`).
2. In `AdminController.ts` (lines 10-17):
   ```typescript
   const GetUsersQuerySchema = z.object({
     role: z.nativeEnum(UserRole).optional(),
     ...
   });
   ```
   `UserRole` in `core/enums/Role.ts` is defined as:
   `PROVIDER = 'PROVIDER'`, `WORKER = 'WORKER'`, `AGENT = 'AGENT'`, `ADMIN = 'ADMIN'` (UPPERCASE).
3. Result:
   When an admin filters by role (e.g. selects "Worker"), the frontend sends `GET /admin/users?role=worker`.
   Zod schema validation immediately throws a `400 Bad Request` with:
   `"Invalid enum value. Expected 'PROVIDER' | 'WORKER' | 'AGENT' | 'ADMIN', received 'worker'"`.
   The user directory crashes and displays an error toast.

Remediation Required:
- Update `admin/users/page.tsx` option values to uppercase (`"WORKER"`, `"PROVIDER"`, `"AGENT"`) 
  or transform to uppercase in `GetUsersQuerySchema` / `adminApi.ts`.

2.4 Admin System Bookings Search Bar (IGNORED QUERY FAILURE)
--------------------------------------------------------------------------------
Affected Components:
- `frontend/src/app/(admin)/admin/bookings/page.tsx`
- `backend/src/modules/admin/controllers/AdminController.ts`
- `backend/src/modules/bookings/repositories/BookingRepository.ts`

Root Cause:
1. In `AdminBookingsPage` (`admin/bookings/page.tsx`, lines 68-75):
   `<Input placeholder="Search by Booking ID..." value={search} ... />`
   Passes `search` to `useGetBookingsQuery`, which sends `GET /admin/bookings?search=booking_123`.
2. In `AdminController.ts` (lines 23-31):
   ```typescript
   const GetBookingsQuerySchema = z.object({
     page: z.string().optional().transform(...),
     limit: z.string().optional().transform(...),
     status: z.nativeEnum(BookingStatus).optional(),
     providerId: z.string().uuid().optional(),
     workerId: z.string().uuid().optional(),
     agentId: z.string().uuid().optional(),
     type: z.nativeEnum(BookingType).optional(),
     // "search" is completely missing!
   });
   ```
3. In `BookingRepository.findManyByFilter`:
   The `whereClause` has no condition for `search`.
4. Result:
   Searching by Booking ID in the admin dashboard returns unfiltered results; search does nothing.

Remediation Required:
- Add `search: z.string().optional()` to `GetBookingsQuerySchema` and `BookingFilter`.
- Add `whereClause: { id: { contains: filter.search, mode: 'insensitive' } }` or OR condition across 
  Booking ID, Provider name, and Worker name in `BookingRepository.findManyByFilter`.
