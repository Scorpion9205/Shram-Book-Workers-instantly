1. EXECUTIVE ASSESSMENT & PRIORITIZATION MATRIX
--------------------------------------------------------------------------------
A deep architectural audit of the SHRAM platform (documented in analyzed.txt) 
revealed that while the domain models, event systems, and UI components are rich 
and feature-complete, several core vulnerabilities and architectural anti-patterns 
exist that threaten security, financial consistency, and production stability.

This remediation plan organizes all findings into 9 progressive, dependent phases.
Each phase includes exact file locations, root cause analysis, step-by-step code 
remediation tasks, and acceptance verification criteria.

Severity Matrix:
- CRITICAL (P0): Security exploits, predictable OTPs, financial balance race conditions.
- HIGH (P1): Dual boot crash risks, static method anti-patterns, naked Error throws.
- MEDIUM (P2): Direct Prisma leaks, missing DB indexes, RTK cache staleness.
- LOW/MAINT (P3): Incomplete module directory structures, config centralization.

2. PHASE 1: CRYPTOGRAPHIC SECURITY & OTP HARDENING (P0 - IMMEDIATE)
--------------------------------------------------------------------------------
Objective: Eliminate predictable pseudo-random OTP generation, standardize OTP 
lengths, enforce Argon2id hashing for work-start OTPs, and implement JWT token 
revocation on logout.

Target Files:
- backend/src/shared/verification/utils/otp.utils.ts
- backend/src/modules/auth/services/AuthService.ts
- backend/src/modules/jobs/services/ApplicationService.ts
- backend/src/modules/instant-requests/services/instant-request.service.ts
- backend/src/modules/auth/services/OTPService.ts

Detailed Tasks:
1.1 Centralize OTP Generation Utility:
    - In `backend/src/shared/verification/utils/otp.utils.ts`, replace `Math.random()` 
      with Node's built-in `crypto.randomInt(100000, 1000000)`.
    - Standardize default OTP length to exactly 6 digits across all modules.
    - Export a unified `generateSecureOtp(digits: number = 6): string` helper.

1.2 Remove Ad-Hoc Inline OTP Generation:
    - In `backend/src/modules/auth/services/AuthService.ts` (line 51):
      Remove `Math.floor(100000 + Math.random() * 900000)` and delegate to `OTPService.request()`.
    - In `backend/src/modules/jobs/services/ApplicationService.ts` (line 115):
      Replace 4-digit `Math.floor(1000 + Math.random() * 9000)` with `OTPService` invocation 
      using `OtpPurpose.WORK_START`.
    - In `backend/src/modules/instant-requests/services/instant-request.service.ts` (lines 405, 760):
      Replace 4-digit `Math.floor(1000 + Math.random() * 9000)` with 6-digit cryptographically 
      secure OTP generated via `OTPService`.

1.3 Enforce Work-Start OTP Security Architecture:
    - Ensure Work-Start OTPs are NEVER stored as plaintext in `Booking.startOtp`.
    - Work-Start OTP must create a dedicated `Otp` record (`purpose = WORK_START`, `channel = SMS`), 
      hashed with Argon2id before storage, sent strictly to the Provider's phone number.
    - Worker enters OTP; backend verifies against the Argon2id hash via `OTPService.verify()`.

1.4 JWT Token Revocation on Logout:
    - In `backend/src/modules/auth/services/AuthService.ts`, inject `ICacheService`.
    - Upon `logout(token, refreshToken)`, extract token JTI or hash and write to 
      Redis blacklist with remaining TTL: `await cache.set(CacheKeys.tokenBlacklist(jti), 'revoked', ttlSeconds)`.
    - In `authenticate.middleware.ts`, check Redis blacklist before accepting any access token.

Acceptance Criteria:
[ ] Zero occurrences of `Math.random()` in backend OTP generation code.
[ ] All OTPs (Auth and Work-Start) are 6-digit numbers.
[ ] Work-Start OTPs are hashed using Argon2id and verified via `OTPService`.
[ ] Blacklisted tokens reject requests with 401 Unauthorized immediately after logout.

3. PHASE 2: FINANCIAL CONCURRENCY & WALLET DATA INTEGRITY (P0 - CRITICAL)
--------------------------------------------------------------------------------
Objective: Prevent financial lost updates and balance overdraft race conditions 
in worker wallet operations.

Target Files:
- backend/src/modules/wallet/services/WalletService.ts
- backend/src/modules/wallet/repositories/WalletRepository.ts
- backend/src/modules/wallet/interfaces/IWalletRepository.ts

Root Cause:
`WalletService.ts` reads balance into memory (`const balance = Number(wallet.balance)`), 
calculates `newBalance = balance +/- amount`, and writes back `updateBalance(id, newBalance)`. 
Concurrent operations overwrite each other, causing balance leakage.

Detailed Tasks:
2.1 Implement Atomic DB Increments/Decrements:
    - In `IWalletRepository` and `WalletRepository`, add atomic methods:
      * `incrementBalance(walletId: string, amount: number, tx?: PrismaTransaction): Promise<Wallet>`
        Implementation:
        `await prisma.wallet.update({ where: { id: walletId }, data: { balance: { increment: amount } } })`
      * `decrementBalance(walletId: string, amount: number, allowNegative: boolean, tx?: PrismaTransaction): Promise<Wallet>`
        Implementation:
        Use an atomic SQL update with a balance check constraint:
        If `allowNegative === false`, execute:
        `await prisma.$executeRaw` or conditional Prisma update:
        `prisma.wallet.update({ where: { id: walletId, balance: { gte: amount } }, data: { balance: { decrement: amount } } })`
        If row count == 0, throw `BusinessException('INSUFFICIENT_WALLET_BALANCE')`.

2.2 Eliminate Non-Atomic Operations in `WalletService.ts`:
    - Refactor `creditWallet` and `debitWallet` to call the atomic repository methods.
    - Remove in-memory balance additions and subtractions.

2.3 Encapsulate Transactions inside Repository:
    - Remove direct `this.prisma.transaction(...)` from `WalletService.ts`.
    - Implement a transaction coordinator pattern or `executeInTransaction` helper on `BaseRepository`.

Acceptance Criteria:
[ ] Concurrent wallet credit/debit operations maintain mathematically exact balances.
[ ] No read-modify-write balance cycles exist in `WalletService`.
[ ] Zero direct `this.prisma.transaction` calls inside `WalletService`.

Detailed Tasks:

    - Convert `InstantRequestService` into an instantiated class extending `BaseService`.
    - Refactor all static methods (`createInstantRequest`, `acceptRequest`, `placeBid`, etc.) 
      into instance methods with injected dependencies:
      `constructor(private readonly instantRequestRepo: IInstantRequestRepository, private readonly cache: ICacheService, private readonly socketService: ISocketService)`.

4.2 Convert `FareService` to Class Instance:
    - Define interface `IFareService`.
    - Convert `FareService` to class extending `BaseService`.
    - Inject `ISkillRepository` and `IPlatformSettingService` via constructor.
    - Remove `static calculateInstantFare`.

4.3 Eliminate `(global as any).deps` in `app.ts`:
    - Create a structured `createApp(container: IDependencyContainer)` factory function in `app.ts`.
    - In `server.ts`, run the async bootstrap sequence first:
      1. Initialize database (Prisma connection).

      5. Start HTTP server and bind Socket.IO.

- backend/src/shared/services/pricing/fare.service.ts (~1 occurrence)

Detailed Tasks:

    - Replace `throw new Error("Worker profile not found")` with:
      `throw new NotFoundException("Worker profile not found")` (HTTP 404).
    - Replace `throw new Error("Worker is not available for bookings")` with:
      `throw new BusinessException("WORKER_UNAVAILABLE", "Worker is not available for bookings")` (HTTP 409).
    - Replace `throw new Error("This request does not support bidding")` with:
      `throw new BadRequestException("This request does not support bidding")` (HTTP 400).
    - Replace `throw new Error("You are not authorized to manage this request")` with:
      `throw new ForbiddenException("You are not authorized to manage this request")` (HTTP 403).
    - Replace `throw new Error("Bid amount must be between...")` with:
      `throw new BadRequestException(`Bid amount must be between ₹${minBid} and ₹${maxBid}`)` (HTTP 400).

5.2 Socket.IO Resilience in `BookingStateService.ts`:
    - Wrap socket broadcast calls in a try-catch block or safe-emitter utility.

Acceptance Criteria:
[ ] Zero naked `throw new Error("...")` in domain services and controllers.
[ ] All API error responses return structured format: `{ success: false, message, errorCode, errors }`.
[ ] Correct HTTP status codes (400, 401, 403, 404, 409) returned instead of generic 500s.
